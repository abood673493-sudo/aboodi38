# الأمان - كيف تُطبَّق القيود فعليًا

هذا المستند يشرح **كيف**، وليس فقط ماذا، لأن الادعاء وحده لا يُثبت شيئًا.

## 1. "لا تنفيذ أوامر حرة من الويب" - التطبيق الفعلي

طبقتان منفصلتان، كل واحدة تتحقق بنفسها دون الوثوق بالأخرى:

1. **`backend/internal/sshmgr`** (داخل عملية الـ API غير المميزة): يتحقق من
   اسم المستخدم/النطاق بتعبير نمطي صارم، ثم يستدعي
   `exec.CommandContext(ctx, "sudo", helperPath, args...)` - **مصفوفة
   argv**، وليس سطر shell، فحتى لو احتوت قيمة على `;` أو `` ` `` أو `$()`
   فلن يكون لها أي تأثير خاص.
2. **`backend/cmd/sshpanel-helper`** (الثنائي الوحيد الذي يعمل كـ root):
   يعيد التحقق من **كل** مدخل بنفسه (لا يثق بالمستدعي)، وينفّذ مجموعة ثابتة
   من الإجراءات المعروفة فقط (`create`, `setpassword`, `rename`, `disable`,
   `enable`, `delete`, `setexpiry`, `uid`, `ipacct`, `cert-issue`,
   `cert-renew`) - لا يوجد إجراء يقبل نصًا حرًا لتنفيذه.

قاعدة الـ sudoers (`deploy/sudoers.d/sshpanel`) تسمح لحساب الخدمة
`sshpanel-api` بتشغيل **هذا الثنائي بالذات فقط**، بمساره الكامل، بدون كلمة
مرور، ولا شيء غيره. تم التحقق من هذا فعليًا أثناء البناء: محاولة
`sudo -u sshpanel-api sudo whoami` تُرفض ("a password is required")، بينما
`sudo -u sshpanel-api sudo /usr/local/bin/sshpanel-helper create ...` تنجح.

كلمات المرور لا تمر أبدًا كـ argument لأمر `passwd` (مرئي لأي مستخدم محلي
عبر `/proc/<pid>/cmdline`)؛ تُمرَّر عبر stdin إلى `chpasswd`.

## 2. عزل الصلاحيات

- عملية `sshpanel-api` (الـ API + وسيط WebSocket/TLS) تعمل بحساب نظام مقيّد
  بلا صلاحيات root إطلاقًا، وبدون shell دخول (`/usr/sbin/nologin`).
- ملف systemd الخاص بها (`deploy/systemd/sshpanel-api.service`) مُقفَل إضافيًا
  بـ `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`,
  `MemoryDenyWriteExecute`, وغيرها - الوصول للملفات مقصور على مسارها
  وملف بيئتها فقط.
- شهادات TLS: `/etc/letsencrypt/live` بصلاحيات root فقط (افتراضي certbot)؛
  `sshpanel-helper` ينسخ نسخة مقروءة فقط لحساب الخدمة إلى
  `/etc/sshpanel/certs/<domain>/` (640 للشهادة، 600 للمفتاح، مملوكة
  لـ `sshpanel-api`) بعد كل إصدار/تجديد. تم التحقق فعليًا من أن حساب الخدمة
  يقرأ نسخته، ولا يقرأ مجلد certbot الأصلي، وأن مستخدمًا آخر لا يقرأ أيًا
  منهما.

## 3. حسابات SSH المُنشأة من اللوحة

- تُنشأ بـ `--shell /usr/sbin/nologin` - لا جلسة تفاعلية، فقط توجيه منافذ/نفق.
- `deploy/sshd/99-sshpanel.conf` يفرض نفس القيد على مستوى sshd لمجموعة
  `sshpanel` (دفاع إضافي حتى لو تغيّر الـ shell يدويًا لاحقًا)، ويعطّل
  X11/agent forwarding.
- انتهاء الصلاحية يُفرض على مستوى نظام التشغيل (`chage -E`) - فحتى لو توقفت
  عملية اللوحة، لا يستطيع حساب منتهي تسجيل الدخول.

## 4. المصادقة والتفويض

- كلمات مرور المديرين: bcrypt. لا كلمة مرور افتراضية أو بيانات تجريبية في
  أي مكان؛ أول مدير يُنشأ حصرًا عبر `bootstrap-admin` التفاعلي.
- قفل تلقائي بعد عدد محاولات فاشلة متتالية (افتراضي 5) لمدة قابلة للضبط
  (افتراضي 15 دقيقة)، ورسالة الخطأ لا تكشف إن كان اسم المستخدم موجودًا أصلًا
  (حتى توقيت الاستجابة مُطابَق عبر مقارنة bcrypt وهمية).
- JWT (HS256) بعمر قصير للوصول (15 دقيقة افتراضيًا) وطويل نسبيًا للتجديد.
- RBAC بثلاثة أدوار مُطبَّقة في middleware الخادم على كل مسار حساس - ليست
  مجرد إخفاء أزرار في الواجهة.
- كل عملية حساسة (دخول، إنشاء/تعديل/تعطيل/حذف حساب، إصدار شهادة) تُسجَّل في
  `audit_log` مع هوية الفاعل والوقت.

## 5. وسيط WebSocket/TLS

- لا يفسّر أو يفحص محتوى البيانات إطلاقًا - تمرير بايتات خام فقط إلى
  `127.0.0.1:<sshd_port>`. المصادقة الفعلية تتم بواسطة sshd نفسه.
- بمجرد ضبط `BRIDGE_DOMAIN`، يرفض أي اتصال يحمل ترويسة `Host` مختلفة (ليس
  "بوابة مفتوحة" لأي خدمة على السيرفر).
- لا علاقة له بإعدادات شبكات الجوال أو تجاوز حدود بيانات مزوّد الاتصال - هو
  ببساطة نقل SSH عبر WebSocket/TLS بديلاً عن TCP الخام، وهي تقنية عامة
  لعبور الجدران النارية التي تحجب المنفذ 22 (مستخدمة أيضًا في VPN/الوصول
  عن بُعد للشركات).

## 6. حدود معروفة (يستحق مراجعتها قبل الإنتاج الفعلي)

- لا 2FA (TOTP) على دخول المدير.
- رموز الوصول (JWT) تُخزَّن في `localStorage` بالواجهة - أبسط من جلسات
  httpOnly cookie لكنها عرضة نظريًا لسرقة عبر XSS لو وُجدت ثغرة حقن في
  الواجهة لاحقًا. يُنصح بإضافة Content-Security-Policy صارم في nginx.
- حد معدل الدخول (rate limit) مطبّق لكل IP داخل عملية الـ API نفسها؛ إن كانت
  اللوحة خلف عدة وسطاء (CDN) يجب ضبط `X-Forwarded-For` بعناية حتى لا يُخدَع.
